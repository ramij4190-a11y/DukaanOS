## 2. Multi-Tenant Retail Domain Model

```
                    ┌─────────────────────────┐
                    │      Tenant / Store     │
                    │       (kirana_id)       │
                    └────────────┬────────────┘
                                 │ 1:N
        ┌────────────────────────┼────────────────────────┐
        ▼                        ▼                        ▼
┌──────────────┐         ┌──────────────┐         ┌──────────────┐
│   Products   │         │  Suppliers   │         │    Users     │
│   Catalog    │         │              │         │(Owner/Staff) │
└───────┬──────┘         └──────┬───────┘         └──────────────┘
        │                       │
        ├───────────────────────┼────────────────────────┐
        ▼                       ▼                        ▼
┌──────────────────┐   ┌──────────────────┐   ┌──────────────────┐
│ Inventory Ledger │   │ Purchase Orders  │   │ Sales Receipts   │
│ (Event-Sourced)  │   │ (Draft/Approved/ │   │ (Items, Quantities│
│                  │   │  Received)       │   │  UPI/Cash/Khata) │
└──────────────────┘   └──────────────────┘   └──────────────────┘
```

### Core Entities:
1. `stores`: Store details, GSTIN, tenant isolation key.
2. `products`: Barcode, SKU, name, category, cost_price, selling_price, min_reorder_level.
3. `inventory_ledger`: Traceable append-only ledger (`OPENING_STOCK`, `PURCHASE`, `SALE`, `DAMAGE_EXPIRED`, `RETURN`, `ADJUSTMENT`).
4. `sales_transactions`: Invoices, line items, timestamps, payment methods.
5. `purchase_orders`: Supplier purchase requests, line items, delivery status, lead time tracking.
6. `daily_forecasts`: Cached predictions generated by the ML engine.

## 3. API Surface Design (REST & Fast Async)

| Endpoint | Method | Purpose |
| :--- | :--- | :--- |
| `/api/v1/auth/token` | `POST` | Store owner & clerk authentication (JWT) |
| `/api/v1/products` | `GET`, `POST` | Product catalog retrieval and SKU creation |
| `/api/v1/inventory/ledger` | `GET` | Audit trail of inventory movements |
| `/api/v1/inventory/reconcile`| `POST` | Physical stocktaking reconciliation |
| `/api/v1/sales` | `POST` | Record checkout counter basket transaction |
| `/api/v1/intelligence/daily-brief` | `GET` | Morning dashboard: sales prediction, low-stock alerts, purchase suggestions |
| `/api/v1/purchase-orders/suggested` | `GET` | Automated ROP-based purchase order recommendations |
| `/api/v1/purchase-orders/approve` | `POST` | Human-in-the-loop PO approval |

## 4. Key Engineering Challenges in Phase 3

### Challenge 03: Idempotency & Concurrency
- Preventing double-recording of sales receipts or duplicate purchase orders when network blips occur.
- Using Redis distributed locks and unique `Idempotency-Key` headers on transaction endpoints.

### Challenge 05: Multi-Tenant Isolation
- Ensuring Store A can never query or mutate Store B's data.
- Tenant context extracted from JWT claims and enforced automatically via PostgreSQL Row-Level Security (RLS) or SQLAlchemy scoped session filters.
